# Серверная часть: живые дуэли, бот, вызовы во всех режимах, друзья и топы (Vercel + Upstash через kv.ts)

Транспорт: HTTP-опрос, ответ на каждую отправку ответов сразу несёт состояние соперника; SSE не берём. Сервер сам выставляет счёт и сам ведёт часы. Оба клиента получают seed и строят тот же набор заданий чистыми генераторами (lib/bank, logic.ts игр). Сервер собирает этот же набор и проверяет каждый ответ и правдоподобное время. Подсказывающего рядом сервер не поймает, но подделку итога и невозможную скорость ловит. Личность без аккаунтов — отдельный подписанный id игрока (cookie inf_pl, не путать с inf_ai устройства ИИ) и публичный код друга BIT-XXXX. На новом телефоне это новый игрок, если не перенести профиль одноразовым кодом со старого. Подбор соперника: Redis-очередь на режим и полосу уровня. Через ~4 с поиск расширяется на соседние полосы, на 9-й секунде предлагается бот. Бот без ИИ: детерминированная «запись» ответов по профилю уровня, считается сервером из seed без записей в Redis. Он честно подписан как «Бит-тренер». Асинхронный вызов в любом режиме — та же дуэль против «призрака», то есть записи ответов вызвавшего. Топ недели и топ мира — сортированные множества Redis, ключ недели меняется сам. В них идут только очки, проверенные сервером. Топ друзей собирается за 4 команды. Живая дуэль стоит ≈ 250 команд Redis (бот ≈ 110), это ≈ $0.0005 сверх бесплатных 500K в месяц. dev и e2e работают на памяти одного процесса. В production без Upstash соцчасть выключена.

## 0. Исходные факты из кода (на них опирается проект)
- `src/server/kv.ts`: при ошибке Upstash и запись, и счётчики молча откатываются в память копии сервера (`safe`). Для лимитов ИИ это нормально, для матчей — нет: разные копии увидят разные состояния.
- Интерфейс `Kv` сейчас умеет только incr/get/list/hash. Для очереди, топов и друзей нужны ZSET, SET, SET NX, MGET, DEL и HSETNX.
- `src/server/ai-guard.ts`: cookie устройства `inf_ai` (HttpOnly, Path=/api, 400 дней, HMAC с `AI_DEVICE_SECRET`) нужна для лимитов ИИ. В ключах Redis IP хранится только как HMAC-хеш.
- `src/lib/text.ts → seeded()/hashString()` и `lib/bank → draw(shape,{skills,count,seed,minLevel,maxLevel})` детерминированы и чисты, поэтому сервер может пересобрать тот же набор.
- `games/truth/logic.ts` (`TruthEngine({skills,mode,seed})`, MODE_CONFIG) уже работает от seed. `games/bit-rush/logic.ts → createStream(seed, masteries, mode)` подстраивается под освоение ученика. Для дуэли освоение надо зафиксировать по полосе уровня.
- `lib/challenge.ts` — вызов на вариант ЕНТ, целиком в URL (#73). Его оставляем как есть: оболочка ЕНТ остаётся тихой и одиночной.
- e2e: Playwright поднимает `next start` одним процессом, значит общая память для двух контекстов браузера есть.
- Next 16: обработчики маршрутов принимают `(req, ctx: RouteContext<'/api/duel/m/[id]'>)` и читают `await ctx.params`. Для побочных действий после ответа есть `after()` из `next/server`.

## 1. Транспорт: опрос с ответом «на попутке», а не SSE (обоснование числами)
**Выбор:** обычный HTTP. Каждая отправка ответа (`POST /api/duel/m/{id}/answers`) сразу возвращает полное состояние матча (`MatchView`). Отдельный опрос `GET /api/duel/m/{id}` нужен, только пока игрок молчит.

**Интервалы опроса:**
- очередь — 1,5 с;
- комната-лобби — 2 с;
- обратный отсчёт — без опроса: `startAt` известен заранее, одна проверка «ready»;
- игра — опрос, если ответа не было 2 с (блиц) или 3 с (обычный);
- итоги — 2 с, пока соперник не закончил, максимум 15 с;
- входящие (приглашения, ответы на вызовы) — 20 с, пока открыт экран «Дуэли», на остальных экранах — один раз при возврате на вкладку.

При `document.hidden` опрос останавливается. При ошибке интервал растёт: 2 → 4 → 8 с.

**Команды Redis на живую блиц-дуэль (60 с, ~30 ответов у каждого):**
- очередь ≈ 20 на игрока (ZPOPMIN, HSET+EXPIRE билета, ZADD, 5–6 опросов по HGET+EXPIRE) → ≈ 40 на матч;
- создание матча ≈ 3;
- игра: на запрос нужен 1 конвейер — k×HSETNX ответов + HSET seen + HGETALL ≈ 3 команды; ~30 запросов на игрока → ≈ 180 на матч;
- завершение ≈ 12 (HSETNX fin, HSET result, ZINCRBY недели ×2, EXPIRE, ZADD/ZINCRBY рейтинга ×2, LPUSH+LTRIM истории ×2);
- опрос итогов ≈ 6.

**Итого:** ≈ 240–260 команд на живой матч и ≈ 110 на матч с ботом: бот ничего не пишет, его прогресс вычисляется. Бесплатного объёма Upstash (500K в месяц) хватит примерно на 2 000 живых матчей. Дальше по тарифу pay-as-you-go ($0.2 за 100K команд — сверить с прайсом при подключении) это ≈ $0.0005 за матч, 10 000 матчей ≈ $5. Вызовы функций Vercel: ≈ 70–90 на матч, каждый ≈ 20–50 мс активного CPU; 10 000 матчей ≈ 0,8 млн вызовов.

**Почему не SSE из Fluid-функции:**
1. Сама функция всё равно должна опрашивать Redis: pub/sub через REST к Upstash — отдельная тема, и в `kv.ts` его нет. Опрос раз в 0,5 с — это 120 команд в минуту на игрока, втрое больше, чем клиентский опрос.
2. Функция держится открытой 60–90 с на каждого игрока: платится время с выделенной памятью, и её жёстко ограничивает `maxDuration`.
3. Мобильные сети и прокси рвут или буферизуют SSE, всё равно нужен переподключённый опрос.
4. Задержка «прогресса соперника» в 1–2 с для полоски «кто впереди» незаметна: победителя решают серверные часы, а не то, что видно на экране.

Если когда-нибудь понадобится настоящий real-time, путь — внешний брокер (Ably/Pusher), это отдельное решение.

**Регион:** функции и база Upstash — в одном регионе, ближайшем к Казахстану (fra1 / eu-central-1). Иначе каждая отправка = RTT до США. Это вопрос к владельцу.

## 2. Личность без аккаунтов: игрок, код друга, новый телефон
**Отдельный id игрока, а не id устройства ИИ.**
- Cookie `inf_pl=<id22>.<sig22>`: HttpOnly, SameSite=Lax, `Path=/api` (нужна и /api/social, и /api/duel), Max-Age 400 дней, Secure в prod.
- Подпись — HMAC от `SOCIAL_SECRET`. Если секрета нет — производный, как `deviceSecret()`: sha256 с солью `informatica-social-v1`. Подписание и проверку выносим из ai-guard в общий `src/server/signed-id.ts`.
- Почему отдельно:
  - у соцчасти своё согласие и своё удаление: «Удалить мой профиль в соревнованиях» не должно сбрасывать лимиты ИИ;
  - публичный код друга не связан с id лимитов;
  - иначе удаление профиля стало бы обходом лимита ИИ.
- Создаётся лениво — при первом `POST /api/social/me` (игрок открыл «Дуэли»). Новых игроков с одного IP — не больше 300 в сутки, как новых устройств в ai-guard.

**Профиль** `pl:{pid}` (HASH, TTL 180 дней, продлевается при активности):
- `name`, `nameState` (ok | filtered | hidden);
- `lv` (уровень, сообщает клиент);
- `fr`, `bn`, `ti` — надетые украшения, только `isCosmeticId`;
- `code`, `lang`;
- `top` (0/1 — участие в общем топе), `ft` (0/1 — видно ли меня в топе друзей);
- `created`, `seen`.

Денормализованная карточка для массового чтения — `pl:c:{pid}` (STRING JSON `{n,lv,fr,bn,ti,code}`, тот же TTL), чтобы топ читался одним `MGET`.

**Код друга** `BIT-7K2Q`:
- алфавит без похожих символов `23456789ABCDEFGHJKMNPQRSTVWXYZ` (30 знаков); 4 знака = 810K кодов;
- выдача: `SET pl:code:{CODE} pid NX`, при 3 коллизиях подряд — 5 знаков.

Код публичный, перебором он не берётся: добавление по коду — это только **заявка**, другой должен принять.

**Новый телефон:** это новый игрок, и экран честно об этом говорит («Друзья и очки привязаны к этому телефону. Переносишь — возьми код переноса на старом»). Перенос:
1. На старом телефоне `POST /api/social/transfer` выдаёт одноразовый 8-значный код: `pl:xfer:{code}` = pid, TTL 15 мин.
2. На новом `POST /api/social/transfer/claim` ставит cookie со старым pid и удаляет код.
3. Неудачных попыток — не больше 10 в час на IP.

Старый телефон потерян → профиль не восстановить до этапа 17. Через 180 дней он сам истечёт.

**Имя из профиля:**
- чистая `src/lib/name-filter.ts → checkName(raw): {ok:true,name}|{ok:false,reason:'empty'|'length'|'chars'|'contact'|'bad'}`;
- длина 2–16, только буквы ru/kk/en, пробел и дефис, без цифровых последовательностей ≥ 4, URL и @;
- нормализация: нижний регистр, латинско-кириллические двойники, 0→о, 3→з, 4→ч, 6→б, @→а, $→s, повторы букв и разделители схлопываются;
- проверка по корням-стоп-словам ru/kk/en (список в `src/lib/name-blocklist.ts`, тесты на обход);
- не прошло → сервер хранит `nameState=filtered`, клиент показывает безопасное имя «Ученик 7K2Q» / «Оқушы 7K2Q» (по коду, на языке смотрящего);
- в профиле подсказка «только имя или ник, без фамилии».

**Кнопка «Пожаловаться на имя»:**
- `POST /api/social/report`; `mod:rep:{pid}` (SET жалобщиков, TTL 90 дней) + запись в `mod:replog` (pushCapped 500) для страницы владельца;
- жалобы от 3 разных игроков → `nameState=hidden` до проверки владельцем;
- `POST /api/owner/social/name {pid, action: allow|hide}` за owner-auth.

Другого свободного текста нет: ни чата, ни подписей.

## 3. Подбор соперника, бот, состояния матча
**Режим дуэли** `DuelModeId` — пара «игра + темп» из белого списка `src/lib/duel/modes.ts`. Первая волна:
- `truth:blitz`, `truth:normal` (утверждения);
- `rush:blitz` (короткие вопросы, освоение зафиксировано по полосе);
- `cipher:normal` (ввод);
- `quiz:blitz` — задания формы `question` с выбором варианта.

Игры с перетаскиванием и падающими карточками (bit-sort, memo, tower, build) — позже: для каждой нужен адаптер проверки.

**Полоса уровня:** band = 1 (ур. 1–4), 2 (5–9), 3 (10–19), 4 (20+), по `TIER_STARTS`. Уровень сообщает клиент. Когда есть серверный рейтинг, полоса = max(по уровню, по рейтингу), чтобы «понизиться до 1-го уровня» ради лёгких побед не работало.

**Очередь** — `du:q:{mode}:{band}:{deckTag}` (ZSET, member = ticketId, score = время входа).
- `deckTag` — отпечаток версии генераторов (как `poolTag`). Во время выкладки клиенты разных сборок не попадут друг к другу: тот же seed у них дал бы разные задания.
- Билет `du:t:{ticket}` (HASH, TTL 20 с, продлевается каждым опросом): pid, lv, band, created, matchId.

Алгоритм `POST /api/duel/queue`:
1. ZPOPMIN своей очереди; до 3 попыток, пропуская истёкшие билеты и свой pid.
2. Нашёлся соперник → создаём матч, пишем `matchId` в его билет, отвечаем `matched`.
3. Не нашёлся → ZADD свой билет, ответ `waiting`.

Опрос `GET /api/duel/queue/{ticket}`:
- HGET matchId + EXPIRE;
- с `widen=1` (через 4 с) — ещё ZPOPMIN соседних полос.

На 9-й секунде (`DUEL_BOT_AFTER_MS`, по умолчанию 9000) клиент показывает: «Живой соперник не нашёлся. Сыграть с Битом-тренером? [Играть с Битом] [Подождать ещё]». Через 3 с без выбора — автоматически бот; «Подождать ещё» даёт ещё 15 с.

`POST /api/duel/queue/{ticket}/bot`:
1. ZREM своего билета.
2. Вернул 0 — нас уже забрали: ждём matchId до 1,5 с и входим в живой матч.
3. Иначе — матч с ботом.

Отмена — `DELETE /api/duel/queue/{ticket}`.

**Бот без ИИ:** `src/lib/duel/bot.ts`, чистый код.
- `botProfile(band, recent?)`:
  - точность по уровням A/B/C — полоса 1: .75/.55/.4, 2: .82/.65/.5, 3: .88/.75/.6, 4: .93/.82/.7;
  - время ответа — логнормальное вокруг `MEDIAN_MS[shape][level]` × множитель полосы (1.4 / 1.2 / 1.0 / 0.85).
- Мягкая подстройка по последним 10 матчам игрока с ботом (`du:bot:{pid}` STRING вида `WWLWL…`, TTL 30 дней): 7+ побед → точность +0,05 и темп ×0,9; 7+ поражений → наоборот. Цель — ~50–60% побед ученика.
- `botTimeline(deck, profile, botSeed, durationMs): {i, ok, t}[]` строится детерминированно. В матче хранится только `botSeed` и профиль, прогресс бота на любой момент считает `botProgressAt(meta, now)`, без записей в Redis.
- **Подача честная:** имя «Бит-тренер» / «Бит-жаттықтырушы», аватар — маскот Бит, метка «бот», строка «Играет как ученик твоего уровня». Человеком не притворяется.
- Победы над ботом не меняют рейтинг и дают в недельный топ не больше 1 очка за победу, до 10 в сутки (`du:botcap:{kzDay}:{pid}`).

**Матч** `du:m:{id}` (HASH, TTL 1 ч; id — 12 знаков base64url):
- мета: `mode`, `seed`, `deckTag`, `n` (размер набора), `kind` (live | bot | ghost | room), `state`, `created`, `startAt`, `endsAt`, `a`, `b` (pid; для бота `bot`, для призрака `ghost:{challengeId}`), `botSeed`, `bp` (профиль бота JSON), `room`;
- поля игроков: `a:{i}` / `b:{i}` = `ok|ms|pts`, `a_seen`, `b_seen`, `a_done`, `b_done`, `a_rdy`, `b_rdy`, `a_rm`, `b_rm`;
- итог: `fin`, `res`, `rm` (id реванша).

Состояния:
- `lobby` — только комната: ждём второго, TTL лобби 10 мин.
- `countdown` — матч создан: `startAt = now + 3500`; клиенты получают `serverNow` в каждом ответе и считают сдвиг часов как `serverNow − (send+recv)/2`.
- `playing` — от startAt до `endsAt`: блиц — startAt + 60 с; «обычный» — startAt + n × потолок на задание, или раньше, если оба `done`.
- `finished` — `now ≥ endsAt + 3 с` или оба `done`. Ответы после `endsAt + 3 с` не принимаются.
- `cancelled` — соперник не подтвердил готовность (`rdy`) за 6 с после создания: матч отменён, оставшемуся сразу предлагается бот («Соперник ушёл — сыграй с Битом»). Сердечко не списано: списание — в начале игры.

**Завершение ленивое**, без cron. Любое чтение, увидевшее условие конца:
1. считает итог чистой `scoreMatch()`;
2. делает `HSETNX du:m:{id} fin 1`;
3. только победитель гонки (1) пишет `res` и через `after()` начисляет топ и рейтинг. Ровно одно начисление.

Никто больше не пришёл — матч просто истекает без очков.

**Обрыв связи:** seat-токен в sessionStorage; вернулся во время игры — продолжаешь, часы не стоят.
- `seen` старше 15 с во время игры → «соперник отключился» на экране; итог по очкам в конце.
- Ушедший до конца с явным `POST /leave` → поражение, если игра началась (защита от «вышел, когда проигрывал»).
- Никто не отключался → победитель по правилам режима.

**Реванш:** `POST /rematch` ставит `a_rm=1`. Когда оба — создаётся новый матч с новым seed, его id лежит в `rm`. Ожидание реванша — 20 с. Реванш = новое занятие = новое сердечко.

**Правила счёта** (`src/lib/duel/score.ts`):
- блиц: сумма очков, при равенстве — больше верных, затем меньше общее время;
- «обычный»: n заданий, больше верных, затем меньше общее время.

То, что на экране «кто лучше и кто быстрее».

## 4. Сервер сам выставляет счёт: что проверяем и что проверить нельзя
**Набор заданий** — `src/lib/duel/deck.ts`, чистый, один код на клиенте и сервере:
- `buildDeck(mode, seed, band): DuelItem[]`;
- `checkAnswer(item, answer): {ok, pts}`.

Внутри — адаптеры к существующим генераторам: `draw('statement'|'short'|'question', {skills: MODE_SKILLS, count: n, seed, minLevel, maxLevel})`, перемешивание вариантов — тем же `seeded(seed ^ i)`.

Ответ кодируется по форме:
- утверждение — `boolean`;
- выбор — индекс варианта после перемешивания;
- ввод — строка через `normalizeAnswer`/`checkInput` из `lib/check.ts`.

**Seat-токен вместо чтения меты:** при создании матча каждому игроку выдаётся `seat = base64url(JSON{m,s,pid,mode,seed,band,n,startAt,endsAt,deckTag}).HMAC(SOCIAL_SECRET)`, передаётся в заголовке `x-duel-seat`. Отправка ответов проверяет подпись и считает правильность чисто, без чтения Redis. Потом один конвейер: `HSETNX a:{i}` на каждый ответ (повтор и вторая вкладка не перезапишут) + `HSET a_seen` + `HGETALL`.

**Что сервер проверяет:**
1. Ответ верен — сервер сам пересобирает задание по seed и индексу.
2. Индекс в пределах набора, каждый ответ засчитан ровно один раз (HSETNX), ответы идут по порядку: `i ≤ число принятых + пачка`.
3. Время по серверу: ответ принят в окне [startAt, endsAt + 3 с].
4. Правдоподобная скорость:
   - клиент шлёт `ms` — время на задание; каждое ≥ `MIN_MS[shape][level]` (утверждение 500 мс, выбор 700, ввод 1200 + 150 на символ ответа);
   - сумма `ms` ≤ (now − startAt) + 1,5 с.
   - Слишком быстрые ответы засчитываются как неверные (`flag:fast`); больше 3 таких в матче — матч не идёт в общий топ и рейтинг (`res.flagged`).
5. Матч и итоги подписаны сервером: подделать счёт в localStorage или в ссылке нельзя.
6. Расхождение `deckTag` → 409 `update_needed` («Обнови страницу — задания изменились»).

**Что проверить нельзя (честно записываем в DECISIONS):**
- подсказчика рядом, калькулятор, поиск в интернете;
- чтение ответов из кода страницы через devtools: seed есть у клиента ради мгновенной реакции игры. Для ребёнка это барьер высокий, но не абсолютный;
- что уровень, о котором сообщает клиент, настоящий (смягчено рейтингом);
- одного человека на двух телефонах — друзья-сообщники, «фарм» побед. Смягчено: рейтинг только за матчи с людьми, за повторную пару в сутки очки убывают (3-й и далее матч той же пары за сутки — 0 очков недели).

Если списывание станет заметно, позже можно ввести «закрытый набор» для общего топа: сервер отдаёт задания без seed и ответов, а правильность сообщает после каждого ответа. Цена — RTT на каждый ответ и ещё одна копия генерации.

**Размер серверной функции:** `lib/bank/index.ts` тянет все банки. Если холодный старт маршрута дуэли окажется больше ~500 мс, нужен `src/lib/duel/banks.ts` — `drawFrom(banks[])` только по файлам банков, нужным режимам дуэли. Измерить в P2 (`scripts/bundle-size.mjs`).

## 5. Комнаты для друзей, живые приглашения, асинхронные вызовы во всех режимах
**Комната — живой бой с другом:**
- `POST /api/duel/room {mode}` создаёт матч в `lobby` и код комнаты из 6 знаков: `du:room:{CODE}` = matchId, `SET NX`, TTL 10 мин.
- Ссылка `/duel/r/{CODE}` уходит в мессенджер через то же меню «Поделиться», что у `/r/`.
- Друг открывает → `POST /api/duel/room/{code}/join` → матч переходит в `countdown`.
- Новый ученик сначала проходит онбординг: ссылку сохраняет `pending-link.ts`, туда добавляем разбор `/duel/r/` и `/c/`.
- Хозяин ждёт в лобби (опрос 2 с), может отменить.
- Ошибки: `full`, `expired`, `self`.

**Приглашение из списка друзей:** `POST /api/duel/invite {friendPid, room}`. Это проверенный друг (SISMEMBER), иначе 403. Пишет `pl:inbox:{friendPid}` (pushCapped 10, TTL 10 мин). Друг видит приглашение во входящих, если открыт раздел «Дуэли» (опрос 20 с) или при возврате на вкладку. Web Push для приглашений — после этапа 17: нужны хранение подписок и согласие.

**Асинхронный вызов в любом режиме = матч против «призрака».**
1. Вызывающий играет обычный проверенный сервером матч (`kind: solo`, тот же движок без соперника) или берёт только что сыгранный живой матч или матч с ботом.
2. `POST /api/duel/challenge {matchId, seat}` сохраняет `ch:{id}` (HASH, TTL 30 дней): mode, seed, band, deckTag, `by` (pid), `res` (счёт, верных, время), `tl` — компактная запись ответов вызывающего `i:ok:t;…` (~300 байт), `count` принявших.
3. Ссылка `/c/{id}` (10 знаков). Превью «Бит-спринт, блиц: 18 очков. Сможешь больше?» — по образцу OG у `/r/`, без имени: имя видит только тот, кто открыл ссылку.
4. Получатель → `POST /api/duel/challenge/{id}/accept` → матч `kind: ghost`. Соперник — призрак, проигрывающий записанную шкалу, как бот: на экране та же полоска «кто впереди», подпись «Запись игры друга».
5. Итог пишется в `pl:inbox:{by}` («BIT-7K2Q принял вызов: 21 против твоих 18») и в `ch:{id}`: последние 20 результатов (LIST).

Один вызов принимает каждый игрок один раз (`ch:{id}:p` SET). Задания обновились (`deckTag` не совпал) → честное «Задания обновились, вызов устарел. Сыграть этот режим заново?».

**Подписывать ли URL?** Для игр не нужно: в URL только id, результат хранится на сервере и проверен им. Вызов на вариант ЕНТ (`/exam/run?…&ch=`) остаётся прежним, в URL и без подписи (#73): пробник — одиночный и тихий, внутрь ЕНТ дуэли не встраиваем.

## 6. Друзья и топы (сортированные множества Redis)
**Друзья:**
- `pl:fr:{pid}` — SET, не больше 100;
- `pl:frq:{pid}` — входящие заявки, SET, TTL 14 дней;
- `pl:blk:{pid}` — SET заблокированных.

Заявка по коду: `pl:code:{CODE}` → pid. Если он мне уже писал — сразу взаимная дружба. Иначе SADD в его `frq`.

Ссылка-приглашение «в друзья» `/f/{token}`: `pl:finv:{token}` = pid, TTL 7 дней, до 20 принятий. Открывший ссылку становится другом сразу: владелец ссылки сам её отправил, это и есть согласие.

Удалить или заблокировать — SREM с обеих сторон.

**Неделя:** ISO-неделя по Астане (UTC+5), `kzWeek(now) → '2026-W41'`. Сброс — в понедельник в 00:00 по Астане.

**Ключи топов:**
- `top:w:{week}` (ZSET pid → очки недели за дуэли, проверенные сервером; TTL 15 дней, EXPIRE при каждом начислении);
- `top:elo` (ZSET pid → рейтинг; всё время = «Топ мира»);
- `top:xw:{week}` (ZSET pid → опыт недели, сообщённый клиентом; только для топа друзей, если владелец согласится, см. вопросы).

Участие в общем топе отдельно: `top:pub:w:{week}` и `top:pub:elo` пополняются только при `top=1`. Иначе игрок есть лишь в топе друзей.

**Очки недели:**
- победа над человеком 3, ничья 2, участие 1;
- победа над ботом 1 (не больше 10 в сутки);
- принятый вызов 1, победа над призраком +1 (не больше 10 в сутки);
- третий и следующие матчи одной пары за сутки — 0.

**Рейтинг:** Эло, K = 24, старт 1000, только за живые матчи с людьми без флага.

**Чтение:**
- Топ недели или мира: ZREVRANGE 0 49 WITHSCORES + MGET 50 карточек = 2 команды. Ответ одинаков для всех: `Cache-Control: public, s-maxage=60`. В памяти копии ещё 30 с кэша.
- «Моё место»: ZREVRANK + ZSCORE = 2 команды, ответ отдельный, private.
- Топ друзей: SMEMBERS + ZMSCORE week + ZMSCORE elo + MGET карточек = 4 команды на любое число друзей. Кэш на клиенте 60 с. Друзья с `ft=0` выводятся без очков («скрыл результат»).

**Обрезка:** при 1 начислении из 50 — ZREMRANGEBYRANK top:elo 0 −50001 (храним 50K лучших).

Опыт недели из клиента подделывается, поэтому в общий топ он не идёт никогда.

**Безопасные значения по умолчанию для несовершеннолетних:**
- общий топ — выключен (`top=0`), включается переключателем на итогах первой дуэли с пояснением «Твоё имя, уровень и очки увидят все»;
- топ друзей — включён;
- в топах — только имя (или «Ученик 7K2Q»), уровень и украшения. Ни города, ни школы.

## 8. Изменения в kv.ts, лимиты, режим без Upstash
**Расширение `Kv`** (обе реализации; в памяти — Map плюс сортировка, тесты на семантику Redis):
- `hset(key, fields, ttl)`, `hsetnx(key, field, value)`, `hgetAllRaw(key)` (строки);
- `setNx(key, value, ttl)`, `getStr(key)`, `mget(keys)`, `del(keys)`, `expire(key, ttl)`;
- `sadd`, `srem`, `smembers`, `sismember`, `scard`;
- `zadd`, `zincrBy`, `zpopmin`, `zrem`, `zrevrangeWithScores`, `zrevrank`, `zmscore`, `zremRangeByRank`;
- `pipeline(ops)` — несколько операций одним HTTP-запросом (в памяти — по очереди).

**Строгий режим:** `getSocialKv()` без отката в память. Upstash настроен, но не ответил → ошибка → 503 `social_unavailable` («Соревнования временно недоступны, учёба работает»). Откат на память при сбое дал бы разные матчи на разных копиях и «у тебя нет друзей».

**Флаг доступности:**
- `socialEnabled() = kv.kind === 'upstash' || process.env.SOCIAL_MEMORY_OK === '1'`;
- в production без Upstash раздел «Дуэли» показывает «Скоро» (флаг отдаёт `GET /api/social/me` как `{enabled:false}`);
- dev и e2e ставят `SOCIAL_MEMORY_OK=1`: один процесс, общая память, всё работает.

**Часы:** `src/server/clock.ts → serverNow()` = `Date.now() + testOffset`. testOffset меняет только тестовый крючок при `DUEL_TEST_HOOKS=1`. Все маршруты дуэлей берут время только отсюда, чистые функции принимают `now` параметром.

**Длительности из env:** `DUEL_BOT_AFTER_MS`, `DUEL_BLITZ_MS`, `DUEL_COUNTDOWN_MS`, `DUEL_READY_TIMEOUT_MS`.

**Лимиты:**
- горячая точка `/answers` — без `kvRateLimit` (лишние 2 команды на запрос): защищают подпись seat, порядок индексов, окно времени и пачка ≤ 5; плюс процессный `rateLimit(pid, 40, 10 с)`;
- `kvRateLimit`:
  - очередь и комнаты — 30 за 10 мин на игрока, 600 на IP-хеш;
  - заявки в друзья — 20 в час на игрока, 60 на IP;
  - неудачный поиск кода — 30 в час на IP;
  - жалобы — 10 в сутки;
  - профиль — 20 в сутки;
  - вызовы — 20 в сутки;
  - перенос — 10 неудач в час на IP;
- новых игроков — 300 в сутки на IP (как в ai-guard).

**Злоупотребления:**
- двойная вкладка — HSETNX + один seat;
- самоматч — pid ≠ pid в очереди;
- фарм парой — убывание очков;
- подделка уровня — полоса по рейтингу;
- спам приглашениями — только друзьям, inbox ≤ 10;
- перебор кодов — лимит по IP + заявка вместо мгновенного добавления.

## 9. Приватность: что храним и сколько
| Данные | Срок |
|---|---|
| Профиль `pl:{pid}`, карточка, код, друзья, заявки (14 дн), блокировки | 180 дн после последней активности |
| Билеты очереди | 20 с |
| Матчи | 1 ч |
| Комнаты | 10 мин |
| Входящие | 10 мин |
| Вызовы | 30 дн |
| История дуэлей игрока `du:h:{pid}` (последние 20: режим, код соперника, счёт, итог, время) | 30 дн |
| Топ недели | 15 дн |
| Рейтинг | пока жив профиль |
| Жалобы | 90 дн |
| Ключи лимитов | ≤ 2 окна |

IP нигде не хранится сырым: только HMAC-хеш в ключах лимитов, как в ai-guard. Профиль не содержит ни IP, ни id устройства ИИ, ни данных учёбы, кроме уровня.

**Удаление:** «Удалить профиль соревнований» в профиле (DELETE /me) убирает всё из таблицы, кроме уже сыгранных строк в чужой истории (там только код) и жалоб. Сброс прогресса в приложении профиль соревнований не удаляет, но предлагает это отдельной кнопкой.

Первый вход в «Дуэли» показывает экран «Что видят другие: имя из профиля, уровень, украшения; можно поменять имя или удалить профиль».

Правовой статус имени несовершеннолетнего как персональных данных — к юристу (этап 17). До него — только имя/ник, фильтр, жалобы и общий топ по выбору.

  3. `POST /test/clock {advanceMs: 20000}` → итоги у обоих совпадают; реванш;
  4. случайный соперник: A ищет один → через 1,5 с предложение Бита → матч с ботом, метка «бот» видна;
  5. вызов `/c/…` от A, B принимает → у A во входящих результат;
  6. топ друзей показывает обоих, общий топ — только того, кто включил.
- Часы браузера — `page.clock`: только для анимаций обратного отсчёта. Решения принимает серверное время через крючок.
