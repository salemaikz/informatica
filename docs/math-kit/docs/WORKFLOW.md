# Как работать с Codex: качественно и дёшево

> **Для кого:** для владельца проекта (не программиста) и для Codex. Здесь описано, как в Matematika идёт работа от задачи до выкладки на сайт: какую модель брать для какой работы, как не сжечь лимит, как не сломать проект и не потерять ключи.
>
> **Откуда факты.** Всё о Codex взято из официальной документации OpenAI на **2026-10-03**, ссылки — в разделе 17. Codex быстро меняется: модели и кнопки переименовывают. Если что-то не совпадает, смотри сжатый мануал https://learn.chatgpt.com/docs/codex-manual.md. У любой страницы документации есть Markdown-версия: добавь `.md` к адресу, и её можно дать Codex прочитать.
>
> **Названия кнопок, меню и команд** (Work in, Advanced, Network secret, `/side`, `/fast` …) — тоже на 2026-10-03, скриншотов нет. Не нашёл кнопку — спроси Codex: «Объясни, как в текущей версии приложения сделать <что>. Сверься с https://learn.chatgpt.com/docs/codex-manual.md».
>
> Пометка **«проверить»** значит, что факт не подтверждён; все такие места и что делать до проверки — в разделе 18. Пометка **«совет»** — это наш вывод.
>
> «В Informatica» — так сделано в образце: его разрабатывали в Claude Code, но принципы те же. Это **справка**: файлов Informatica (её `CHANGELOG`, `HANDOFF`, промптов) в наборе нет, кроме образцов кода в `reference/`. Её опыт пересказан в `docs/CONCEPT.md`, раздел 10; её решения #1–#20 переписаны для математики в `docs/DECISIONS.md` под теми же номерами.
>
> Что лежит рядом: правила для Codex — `AGENTS.md`, готовые тексты запросов — `docs/PROMPTS.md`, этапы — `docs/ROADMAP.md`.

## 0. Десять правил на одной странице

1. **Одна задача — один чат.** Если тема сменилась, открой новый чат и начни его с `docs/HANDOFF.md`.
2. **Сначала план, потом код.** Для большой задачи — `/plan`, затем ТЗ в `docs/tasks/<имя>.md`.
3. **Модель подбирай по сложности** (таблица — 5.3). Думать и решать — GPT-6.1 Sol · Medium (трудное — High). Делать по готовому ТЗ — Sol · Light/Medium или Luna · High. Механика — GPT-6 Luna · Light/Medium.
4. **В задаче всегда четыре части:** цель, контекст (пути к файлам), ограничения, «готово, когда».
5. **Перед задачей `git status` должен быть чистым** — это точка, к которой можно откатиться. После задачи — коммит.
6. **После исполнителя — независимое ревью** (`/review` в новом чате). В Informatica ревьюер каждый раз находил настоящие баги.
7. **Проверяй командами, а не глазами:** `npm run typecheck && npm run lint && npm test && npm run build`. Глазами смотри только то, чего не поймает тест: телефон, тёмную тему, казахский текст.
8. **Путь изменения на сайт:** ветка → превью на Vercel → смотришь на телефоне → правки → владелец принимает → слияние в `main`. Слияние в `main` и есть выкладка.
9. **Ключ OpenAI хранится только в `.env.local` и в настройках Vercel.** Не в чате, не в коде, не в облаке Codex.
10. **После каждой задачи обновляй** CHANGELOG, ROADMAP и HANDOFF. При необходимости ещё DECISIONS, ARCHITECTURE и AGENTS.md.

## 1. Подготовка (делается один раз)

### 1.1 Аккаунты и деньги

| Что | Зачем | Цена (на 2026-10-03) | Где |
|---|---|---|---|
| **ChatGPT Plus** | Codex, то есть разработка | $20/мес | chatgpt.com |
| **GitHub** | хранит код; облако Codex и Vercel берут код отсюда | бесплатно, приватный репозиторий | github.com |
| **Vercel** | сайт; автоматическая выкладка после каждого push | бесплатный тариф Hobby. Условия коммерческого использования — **проверить** до платного запуска | vercel.com |
| **OpenAI API** | ключ для ИИ внутри приложения: наставник «Пи», подсказки, проверка фото | оплата за токены, отдельный счёт | platform.openai.com |

- **Что даёт Plus.** Codex в вебе, в CLI, в IDE, на iOS и в приложении для ПК. Облачные задачи, авторевью кода, модели GPT-6.1 Sol и GPT-6 Luna, докупка кредитов. Тариф Pro (от $100) сейчас снимает 5-часовой лимит. Free и Go дают только Luna и подходят лишь для лёгких задач.
- Codex теперь встроен в ChatGPT: режим **Codex** находится рядом с Chat и Work. **ChatGPT Work и Codex тратят один общий лимит.**
- **Подписка ChatGPT и OpenAI API — разные счета.** Plus не оплачивает API, а API не даёт доступа к Codex.
- **В Codex входи только через «Sign in with ChatGPT».** Если войти API-ключом, работа Codex будет списываться по тарифам API, а облако и ревью в GitHub станут недоступны.

### 1.2 Что установить

1. **Приложение ChatGPT для ПК** (macOS, Windows, Linux) и в нём режим **Codex**. Это главный инструмент. На Windows его ставят из Microsoft Store или командой `winget install --id 9PLM9XGG6VKS -s msstore`.
2. **Git и Node.js (LTS).** Если не знаешь, есть ли они, спроси Codex: «Проверь, установлены ли git и Node.js и подходят ли версии для Next.js 16. Скажи, что поставить». Это совет: Codex сам проверит и подскажет.
3. **CLI** (`npm install -g @openai/codex`) и расширение для VS Code — по желанию. Новичку хватит приложения.

### 1.3 Настройка Codex

- **Где идёт работа — Local**, то есть на этом компьютере. Так видно diff (что изменилось), можно запустить сайт и смотреть его в браузере. Локальные файлы и процессы в облако не переносятся. **Cloud** нужен для длинных фоновых задач и параллельной работы (раздел 5.6).
- **Права — «Ask for approval»** (так по умолчанию, и OpenAI советует начинать с него). Codex правит файлы и запускает команды в папке проекта, а перед выходом за её пределы (файлы вне проекта, сеть) спрашивает разрешение.
  - «Approve for me»: эти запросы оценивает отдельный агент-ревьюер. Включай, когда освоишься.
  - **«Full access» не включать.** На Windows OpenAI прямо предупреждает о риске потери данных.
- **Модель по умолчанию** задаётся в файле `~/.codex/config.toml`, он общий для приложения, CLI и IDE:
  ```toml
  model = "gpt-6.1-sol"
  model_reasoning_effort = "medium"
  ```
  Это умолчание для прораба. В чате исполнителя или механики модель и усилие переключаешь вручную в начале чата (5.4).
- **MCP-серверов — как можно меньше.** Каждый добавляет текст в каждую сессию. Ненужные выключай.
- **Проверка, что Codex видит правила.** В новом чате напиши: «Перескажи в 5 пунктах правила из AGENTS.md. Код не меняй». В CLI: `codex --ask-for-approval never "Summarize the current instructions."`. Правки в AGENTS.md подхватываются **только в новом чате**.

### 1.4 Репозиторий

Порядок для новичка (подробно, с готовыми фразами — `README.md`, раздел 6, шаги 3–9):
1. GitHub → **New repository** → имя `matematika`, тип **Private**, без галочек README и .gitignore.
2. На компьютере — папка `matematika`, в неё **содержимое** набора: `AGENTS.md`, `README.md`, `docs/`, `reference/` («корень» — это сама папка `matematika`).
3. Открыть папку в Codex (1.3). Git-команды ты не набираешь: Codex делает `git init`, `.gitignore` и первый коммит по фразе из README, шаг 6.
4. Этап 0 — П-0 из `docs/PROMPTS.md` (кода ещё нет).
5. Этап 1.1 — П-1.1: Codex создаёт каркас Next.js и `package.json`. **До этого `npm run …` не работают.**

`.gitignore` (по образцу Informatica; Codex создаёт его при первом коммите):
```gitignore
node_modules/
.next/
out/
build/
.vercel
*.tsbuildinfo
next-env.d.ts
.DS_Store
*.pem
npm-debug.log*
# ключи — никогда в git
```

Перед первым коммитом проверь, что ключ не попадёт в git: `git check-ignore .env.local` должна напечатать `.env.local`. Если ничего не напечатала, файл **не защищён**, и коммитить нельзя.

### 1.5 Облачное окружение Codex (когда понадобится)

1. Новая задача → **Work in → Cloud → Select environment → Create environment**.
2. Выбрать репозиторий `matematika`. Если появится «Connect GitHub», подключить.
3. Нажать **Get started**. Codex сам осмотрит проект, поставит зависимости и запишет **Install script** (установка) и **Start skill** (запуск). Затем **Publish**.
4. **Интернет:** включить «Allow Codex to access internet» и выбрать пресет **Package managers** (npm, GitHub и т. п.). Вариант «All (unrestricted)» не нужен.
5. **Секреты: `OPENAI_API_KEY` приложения в облако не класть.** Тесты работают без ключа, потому что ИИ в них подменяется (`docs/AI.md`, раздел 13). Если живая проверка ИИ в облаке всё же нужна:
   - ключ кладётся только как **Network secret** для домена `api.openai.com`; программа видит заглушку, настоящее значение подставляет прокси;
   - ключ должен быть **отдельным**, с жёстким лимитом расходов.
6. Окружение поменялось → **Edit → Republish**. Каждая задача получает свою чистую копию опубликованного окружения.

Что нужно знать об облаке:
- на Plus у виртуальной машины 2 vCPU, 8 GiB памяти и 8 GiB диска;
- задача хранится 7 дней после последней активности;
- управлять браузером в облаке нельзя, поэтому скриншоты и проверку «глазами» делаем локально;
- личные skills с компьютера в облако не попадают, а skills из репозитория (`.agents/skills/`) — попадают.
- **Проверить:** ставится ли Chromium для `npm run e2e` (`npx playwright install chromium`) и нужен ли в облаке `NODE_USE_ENV_PROXY=1` для запросов к OpenAI (в облаке Claude Code для Informatica он был нужен). До проверки e2e и живой ИИ — только локально (раздел 18).

### 1.6 Vercel (сайт)

1. vercel.com → войти через GitHub.
2. **Add New → Project → Import** репозитория `matematika` → **Deploy**. Next.js Vercel распознаёт сам.
3. **Settings → Environment Variables** — переменные из `docs/ARCHITECTURE.md`, раздел 21:
   - `OPENAI_API_KEY` — для **Production**; для Preview — по желанию, если ИИ нужен и на превью;
   - модели задавать не обязательно, умолчания прописаны в коде.
   - Новые значения переменных применяются только к **новым** сборкам. После изменения нажми **Redeploy**.
4. **Production branch — `main`.** Где это в настройках (Settings → Git), **проверить**.
5. Что получается дальше — в разделе 10.

### 1.7 OpenAI API (ИИ внутри приложения)

Подробно — в `docs/AI.md`, раздел 9. Коротко:
1. На platform.openai.com создать отдельный Project «matematika» и ключ в нём.
2. **Project settings → Limits → Spend → Monthly spend limit**, включить **Enforce a hard limit**. На старте хватит $10–20 (совет). Добавить Spend alert на 50 %.
3. Ключ положить в `.env.local` (образец — `.env.example`) и в Vercel. Больше никуда.

## 2. Цикл этапа

Так работали в Informatica, и так же работаем здесь. **Этап закрыт только тогда, когда его принял владелец.** До этого у него статус «ждёт приёмки».

**Кто есть кто.** «Прораб», «исполнитель», «ревьюер» — не люди и не особые режимы, а **отдельные чаты Codex с разной выбранной моделью**: прораб — чат на GPT-6.1 Sol · Medium, исполнитель — **новый** чат на модели подешевле, ревьюер — ещё один новый чат. **Ты сам код и ТЗ не пишешь:** открываешь новый чат, выбираешь модель из строки над промптом, вставляешь промпт из `docs/PROMPTS.md`, отвечаешь на вопросы и смотришь результат. В этапе 1 общие файлы (шаг 5) создают сами промпты с ролью «Прораб» (например, стор и словарь — П-1.4, типы — П-1.6а).

| # | Шаг | Кто и на какой модели | Что получается | Промпт (`docs/PROMPTS.md`) |
|---|---|---|---|---|
| 1 | Старт: прочитать `docs/HANDOFF.md` и текущий этап в `docs/ROADMAP.md` | механика, Luna · Medium | 3–5 строк: где мы и что дальше | Т-8а |
| 2 | План этапа: `/plan`, не больше 10 пунктов, вопросы владельцу | прораб, Sol · Medium (для архитектуры — High) | план | П-<этап> с пометкой «сначала план» |
| 3 | «Ок» плану, ответы на вопросы | **владелец** | — | — |
| 4 | Нарезка на задачи и ТЗ к каждой в `docs/tasks/<имя>.md` | прораб | файлы ТЗ; в каждом есть «готово, когда» и модель исполнителя | П-<этап> с ролью «Прораб»; урок — Т-1а; игра — Т-4а |
| 5 | Общие файлы: `lib/types.ts`, `lib/store.ts`, `i18n/dict.ts`, реестры | прораб | каркас, на котором исполнители не мешают друг другу | тот же промпт прораба |
| 6 | Исполнение: каждая задача в своём новом чате (раздел 5.6) | исполнитель, Sol · Light/Medium или Luna · High | код, тесты, отчёт на 5–10 строк | П-<этап> с ролью «Исполнитель»; Т-1б, Т-4б |
| 7 | Проверки (раздел 8) | исполнитель сам | все команды зелёные | строка «Проверка» в том же промпте |
| 8 | Независимое ревью `/review` в **новом** чате (раздел 7) | ревьюер, Sol · Medium | список проблем | Т-6, пункт 1 |
| 9 | Исправления, затем повторный `/review` | исполнитель | — | чат исполнителя или Т-5 |
| 10 | Сборка частей вместе, финальная проверка, документация, коммит | прораб | CHANGELOG, ROADMAP, HANDOFF | Т-7, Т-8б |
| 11а | Скриншоты 360/390 px в светлой и тёмной теме на ru и kk (8.3) | механика, Luna · Light/Medium | короткий отчёт | строка «Проверка» в промпте |
| 11б | `npm run review:kk` — вычитка казахского. Платно: с этапа 2, когда в `.env.local` есть ключ; только с «ок» владельца | Codex в режиме **Local** на компьютере владельца (в облаке ключа нет) | правки приняты или отклонены | Т-9 |
| 12 | Push ветки → превью на Vercel | Codex | ссылка на превью | строка «Сдать» в промпте |
| 13 | Владелец проходит этап **на телефоне** и пишет замечания с номерами | **владелец** | список замечаний | — |
| 14 | Правки маленькими задачами (шаги 6–12) | исполнитель | — | Т-5 (один баг), Т-11 (список) |
| 15 | Приёмка → PR в `main` → продакшен → открыть публичный адрес с чужого телефона | **владелец** + Codex | этап ✅ | Т-6 |

**«Готово, когда» — это то, что можно увидеть.** Примеры из Informatica:
- «в режиме „Спокойно“ любую игру можно пройти без стресса; калькулятор открывается из любого места; ответы отзываются анимацией и звуком»;
- «вы проходите новый урок и говорите: понятно и интересно».

**Замечания нумеруй.** У каждого замечания владельца есть номер, а у номера — этап, на котором его решают. В Informatica после первой публикации пришло 25 замечаний, и все они разложены по этапам (`docs/CONCEPT.md`, раздел 10).

**Статусы в планах:** ✅ сделано · 🔜 сейчас · ⏳ в очереди · 💡 идея.

## 3. Размер задачи и нарезка

- **Мелкую и ясную задачу** (до 3 файлов, понятно, что делать) Codex делает сразу.
- **Для большой задачи нужен план и «ок» владельца.** Большая — это:
  - больше 3 файлов;
  - типы или стор;
  - промпты ИИ;
  - архитектура;
  - неясная цель.

  Это правило из `AGENTS.md`, раздел 2.
- **Мерка:** одна задача даёт **один результат, который можно проверить за 5 минут**. OpenAI советует то же: «Start with one result you can review».
- **Длинную работу дели на вехи** (Milestone 1, 2, …) и проверяй каждую.
- **Порядок — по зависимостям**, как в Informatica (`docs/DECISIONS.md`, #18): сначала то, на чём строится остальное.
  - Фундамент: проверка ответов, банк заданий, анимации, «Помощники».
  - Методику отрабатываем на **одном** уроке и только потом тиражируем.
  - Игры появляются, когда в курсе уже несколько тем.
  - Облако — раньше чатов и конспектов.
- **Пример нарезки из Informatica (этап 2).** Прораб сделал типы, ТЗ и структуру курса. Затем 3 исполнителя работали параллельно:
  1. сцены и песочницы;
  2. новые шаги в плеере;
  3. тексты 4 уроков на ru и kk.

  Потом прораб сделал вычитку, собрал части вместе и проверил всё в браузере.
- **Для большого продуктового выбора** (какие игры, какая карта курса) в Informatica собирали «панель». Три «дизайнера» смотрели с разных сторон: наука запоминания, игровой азарт, стоимость. Они предложили 15 концепций. Двое «судей» оценили их: строгий учитель ЕНТ и защитник интересов подростка. Прораб выбрал лучшее.
  - **Панель не обязательна.** На этапах 0–2 она не нужна, а игры для Matematika уже описаны в `docs/GAMES.md`. Максимум раз на этап (совет).
  - Дешёвый вариант (совет) — один чат прораба, Sol · High, без субагентов (они дороже, 5.6):
    ```
    /plan Код не пиши. Нужно выбрать <что>. Шаг 1: три «дизайнера» — наука
    запоминания, игровой азарт, стоимость и переиспользование — предлагают по 5
    концепций. Шаг 2: два «судьи» — строгий учитель ЕНТ и защитник интересов
    подростка — ставят каждой 1–5 и пишут одну строку «почему». Шаг 3: выбери 3–4
    лучших. Ответ — таблица, потом жду моего выбора.
    ```
- **До вёрстки большого нового экрана** покажи владельцу 2–3 эскиза. Урок Informatica: карту курса «кружочки вниз» пришлось переделывать.

## 4. Как писать задачу Codex

### 4.1 Четыре части (официальный совет OpenAI)

| Часть | Что писать |
|---|---|
| **Цель** | Что изменить или сделать и зачем. Одно предложение. |
| **Контекст** | Какие файлы, доки и ошибки важны. Конкретные пути и разделы, например `docs/DESIGN.md` раздел 7, `reference/src/lib/store.ts`. |
| **Ограничения** | Что можно менять, что нельзя. Стандарты. Без новых зависимостей. Тексты ru/kk — давай готовые. |
| **Готово, когда** | Что должно быть правдой в конце: что видно на экране, какой тест зелёный, что баг больше не воспроизводится. |

### 4.3 ТЗ для исполнителя (`docs/tasks/<имя>.md`)

ТЗ пишет прораб, а исполнитель выполняет его в новом чате, часто на более дешёвой модели. Поэтому ТЗ должно быть таким, чтобы **ничего не пришлось додумывать**. Папки `docs/tasks/` в наборе нет: её создаёт прораб вместе с первым ТЗ (П-1.6а — `docs/tasks/player.md`).

Готовые промпты, которые пишут ТЗ, — в `docs/PROMPTS.md`: паспорт урока — Т-1а, ТЗ игры — Т-4а (поля игры — `docs/GAMES.md`, 14.2; промпт исполнителю — 14.4). Для остального — этот шаблон:

```markdown
# ТЗ: <название> (этап <N>, ветка <имя>)
Модель исполнителя: <модель · усилие>. Части: <1, 2 … — если ТЗ делится>.
## Цель — одно предложение.
## Прочитать — пути и разделы; образцы из reference/.
## Файлы — создать: … / можно менять: … / не трогать: types.ts, store.ts, dict.ts, реестры.
## Интерфейсы — типы, props, сигнатуры, откуда данные.
## Тексты ru/kk — полным списком (ключ: ru / kk).
## Числа — px, мс, лимиты, очки.
## Крайние случаи — список.
## Готово, когда — что видно на экране; какие тесты зелёные.
## Проверка — команды.
```

Что обязательно в ТЗ:

- **Файлы поимённо:** какие создать и какие можно править. Отдельно — какие не трогать: `types.ts`, `store.ts`, `dict.ts`, реестры правит только прораб.
- **Интерфейсы:** типы, props, сигнатуры функций, откуда брать данные.
- **Все тексты на двух языках** — полным списком. Исполнитель не должен выдумывать строки.
- **Числа:** размеры в px, время в мс и с, лимиты, формулы очков.
- **Крайние случаи:** двойной тап, Enter, пустой ввод, деление на 0, `0,5` = `1/2`, ширина 360 px, «Меньше анимаций».
- **«Готово, когда»** и команды проверки.
- **Модель исполнителя:** какую взять (раздел 5).

В Informatica у ТЗ на игру были подзаголовки ENGINE / FILES / ROUND FLOW / TIMER / SCORING / LAYOUT / JUICE / KEYBOARD / EDGE CASES / ACCESSIBILITY / STRINGS ru/kk.

### 4.6 Плохо и хорошо

| Плохо | Хорошо |
|---|---|
| «Сделай красивую главную» | «На `/learn` карточка „Следующий урок“ по `docs/DESIGN.md`, раздел 7: `ButtonLink` на всю ширину, прогресс-бар `ProgressBar`, цвета `primary`. Готово, когда на 360 px всё видно без прокрутки» |

| «Изучи проект и скажи, что улучшить» | «Прочитай `docs/HANDOFF.md`. Предложи 3 следующих шага по `docs/ROADMAP.md` с моделью для каждого. Код не меняй» |

### 4.7 Фразы, которые помогают

- «**Сначала задай мне вопросы** и оспорь мои допущения, код пока не пиши» — когда задача размыта.
- «**Действуй сам, спрашивай только перед необратимым**» — когда модель засыпает вопросами. Особенно GPT-6 Astra: она чаще уточняет.
- «**Если не получилось — прямо напиши**, что именно и почему».
- «**Отдели обязательное от желательного**».
- «**Ответ — 5–10 строк**, без пересказа кода, с путями файлов».
- «**Объясни простыми словами**, что мне нажать» — если ответ непонятен.
- «**Предложи 2–3 варианта** с плюсами и минусами» — для решений «на вкус».

### 4.8 Частые ошибки (официальный список OpenAI)

- Постоянные правила пишут в каждом промпте, а не в `AGENTS.md` или skill.
- Не объяснили, как собрать и протестировать проект. У нас это раздел 9 `AGENTS.md`.
- Пропустили план на сложной задаче.
- Дали полный доступ к компьютеру, не разобравшись, что это значит.
- Запустили параллельные задачи на одних и тех же файлах без worktree.
- Поставили задачу по расписанию раньше, чем она надёжно заработала вручную.
- Следили за каждым шагом вместо того, чтобы заниматься другим.
- **Вели весь проект в одном чате.**

### 5.3 Лестница «прораб и исполнители» для Matematika

Это правило Informatica, перенесённое на Codex. **Сильная модель думает и проверяет, дешёвая делает по готовому ТЗ.**

| Сложность | Модель · уровень в Codex | Примеры в Matematika |
|---|---|---|
| **Думать и решать** (прораб) | **GPT-6.1 Sol · Medium**. Трудное — High или Extra High. GPT-6 Astra · Light/Medium — только если Sol не справился дважды | план этапа; ТЗ в `docs/tasks/`; `lib/types.ts`; `lib/store.ts` и миграции; устройство разбора выражений `lib/math/*`; промпты ИИ (`src/server/prompts.ts`); сложные баги (гонки, таймеры); сборка частей вместе; решения в DECISIONS |
| **Работа по чёткому ТЗ** (исполнитель) | **GPT-6.1 Sol · Light/Medium** или **GPT-6 Luna · High** (Luna · Extra High — если ТЗ длинное и строгое) | экран или компонент по `docs/DESIGN.md`; мини-игра по `docs/tasks/game-<id>.md`; генератор заданий по формуле; тесты; черновик урока по ТЗ; перевод ru→kk; документация |
| **Механика** | **GPT-6 Luna · Light/Medium** | найти, где используется X; добавить ключи в `dict.ts` по готовому списку; однотипные правки во многих файлах; прогнать тесты и пересказать только ошибки; скриншоты; запись в CHANGELOG по готовому списку |
| **Ревью** | **GPT-6.1 Sol · Medium**, новый чат | `/review` по разделу «Code Review Rules» в `AGENTS.md` и списку рисков (раздел 7) |
| **Человек** | владелец | приёмка, вкус («понятно и интересно?»), деньги, необратимые действия |

Правила, перенесённые из Informatica:
- **Сначала ТЗ, потом исполнитель.** Дешёвой модели дают конкретную спецификацию: файлы, интерфейсы, критерии готовности. Не «сделай красиво».
- **Результаты исполнителей — короткие выжимки.** Большие файлы и логи прораб целиком не читает.
- **Проверку (тесты, скриншоты) делает дешёвая модель.** Решение «принять или исправить» принимает прораб.
- **Независимые куски делаются параллельно, у каждого исполнителя свои файлы.** Общие файлы правит только прораб.
- **Сильная модель на каждый запрос ученика — никогда.** Это про приложение, а не про Codex. Лестница моделей внутри приложения — в `docs/AI.md`, раздел 2.

Как было в Informatica (Claude Code) и как это переносится в Codex:

| Informatica | Matematika (Codex) |
|---|---|
| `opus`, effort high — прораб | GPT-6.1 Sol · Medium/High |
| `sonnet`, effort medium — по ТЗ | GPT-6.1 Sol · Light/Medium или Luna · High |
| `haiku`, effort low — механика | GPT-6 Luna · Light/Medium |
| субагент с другой моделью | новый чат с другой моделью или свой субагент из `.codex/agents/` (5.7) |
| параллельные исполнители | облачные задачи или локальные worktree (5.6) |
| независимый ревьюер | `/review` в новом чате или `@codex review` в PR |

### 5.4 Как переключать модель

- **Приложение и IDE:** переключатель модели и уровня под полем ввода. Есть слайдер «Power» с готовыми наборами и пункт **Advanced** для точного выбора; что в нём доступно, зависит от плана. Команды `/model` и `/reasoning`.
- **CLI:** `/model` (там же «More reasoning…» для Max/Ultra); запуск `codex -m gpt-6-luna`.
- **По умолчанию** — в `~/.codex/config.toml` (раздел 1.3): GPT-6.1 Sol · Medium, то есть прораб.
- **Правило для новичка:** в начале **каждого нового** чата посмотри строку над промптом в `docs/PROMPTS.md` (или таблицу 5.3) и выставь модель и усилие, **до** отправки первого сообщения. Для прораба менять обычно нечего; для исполнителя и механики — переключить.
- **Codex сам модель не меняет.** Модель выбирает владелец в начале чата. Поэтому прораб в конце отчёта пишет, **на какой модели делать следующий шаг** (`AGENTS.md`, раздел 2).

### 5.5 Как прораб передаёт работу исполнителю (по шагам)

1. **Чат A**, Sol · Medium, режим плана: «Составь ТЗ для <задача> по шаблону `docs/WORKFLOW.md` 4.3, сохрани в `docs/tasks/<имя>.md`, раздели на части и для каждой укажи модель». Владелец читает и даёт «ок».
2. **Чат B** (новый), Luna · High или Sol · Light: «Выполни `docs/tasks/<имя>.md`, часть 1. Сдать отчёт на 5–10 строк».
3. **Чат C** (новый), Sol · Medium: `/review` с фокусом «Code Review Rules из AGENTS.md и „Готово, когда“ из `docs/tasks/<имя>.md`».
4. **Чат B** или новый: исправить найденное и снова сделать `/review`.
5. **Прораб:** собрать части вместе, обновить документацию и HANDOFF, сделать коммит и push. Владелец смотрит превью.

### 5.6 Параллельная работа

- **Облачные задачи.** Каждая работает в своей изолированной копии и выполняется, даже когда компьютер выключен. Результат — diff, коммит или PR. Удобно, когда кусков несколько и они не пересекаются.
- **Локально — только через worktree.** Это вторая рабочая папка того же репозитория, и у каждого чата она своя. Без worktree параллельные чаты правят одни и те же файлы. В приложении: кнопка **Create branch here**, затем commit, push, PR.
- **Субагенты** запускаются только по прямой просьбе: «запусти двух агентов…», «по агенту на пункт». Исключение — уровень Ultra, он раздаёт работу сам. Каждый субагент **тратит свои токены**. OpenAI советует параллелить в основном чтение (исследование, тесты, сортировку), а параллельную запись кода — осторожно, из-за конфликтов. Встроенные агенты: `default`, `worker` (реализация), `explorer` (чтение кода). Без настройки субагент работает на модели родителя.
- **Правило Informatica:** у каждого исполнителя свои файлы. Общие (`lib/types.ts`, `lib/store.ts`, `i18n/dict.ts`, реестры игр и уроков) правит только прораб — до раздачи задач или после.
- **Как проверить сохранённую версию, пока исполнители ещё работают.** Попроси Codex: «Проверь последний коммит в отдельном worktree, мои незакоммиченные файлы не трогай». Подсказка для Codex (приём из Informatica, её делали в Linux-облаке):
  - **Linux и облако:**
    ```bash
    git worktree add <временная-папка>/wt HEAD
    cp -al node_modules <временная-папка>/wt/node_modules
    ```
    Символическая ссылка на `node_modules` не подойдёт: Turbopack её не принимает.
  - **Windows и macOS:** `cp -al` там не работает — в worktree сделать `npm ci` (дольше, но надёжно).
- **Проверить:** есть ли сейчас «несколько вариантов одной задачи» (Best-of-N) в облаке — в текущей документации не найдено.

### 5.7 Свои субагенты на дешёвой модели (по желанию)

Файлы лежат в `.codex/agents/<имя>.toml` (для проекта) или в `~/.codex/agents/` (для всех проектов). Поля: `name`, `description`, `developer_instructions` и по желанию `model`, `model_reasoning_effort`, `sandbox_mode`. Пример OpenAI: исследователь на `gpt-6-luna` + `high` и ревьюер на `gpt-6.1-sol` + `medium`, оба только читают. Точный синтаксис сверить с https://learn.chatgpt.com/docs/agent-configuration/subagents. Работают ли проектные агенты в облачных задачах — **проверить**.

```toml
# .codex/agents/explorer-luna.toml — дешёвый поиск, ничего не меняет
name = "explorer-luna"
description = "Найти файлы и места в коде, ответить коротко. Ничего не меняет."
developer_instructions = """
Отвечай по-русски, 5–10 строк: пути и номера строк, без пересказа кода.
Не читай node_modules/, .next/, package-lock.json, reference/ целиком.

model_reasoning_effort = "medium"

```

```toml
# .codex/agents/reviewer.toml — независимое ревью
name = "reviewer"
description = "Ревью изменений по разделу Code Review Rules в AGENTS.md. Только читает."
developer_instructions = """
Ищи баги, а не стиль. Список рисков — docs/WORKFLOW.md, раздел 7.
Для каждой проблемы: файл и строка, что сломается, как повторить. Сначала самое опасное.

model = "gpt-6.1-sol"
```

Как вызвать: «Запусти субагента explorer-luna: найди все места, где проверяется десятичная запятая».

## 6. Экономия токенов: правила

Каждое правило проверено на Informatica или взято из советов OpenAI.

1. **Одна задача — один чат.** По OpenAI, один чат на весь проект раздувает контекст и ухудшает результат.
2. **Следи за контекстом:** `/status` показывает, сколько его занято.
   - **Занято больше 50 %** — обнови HANDOFF и открой новый чат (правило `AGENTS.md`).
   - **Длинная задача** — `/compact` сжимает историю. Codex сжимает и сам, но вовремя сделанный `/compact` дешевле.
   - **Побочный вопрос** — `/side`: основной чат не засоряется.
   - **Попробовать другой путь** — `/fork`.
   - **Новый чат в CLI** — `/new`.
3. **HANDOFF.md вместо «вспомни, что мы делали».** Новый чат начинается так: «Прочитай `docs/HANDOFF.md` и текущий этап в `docs/ROADMAP.md`. Скажи в 3–5 строках, где мы. Код не меняй».
4. **Давай пути, а не «найди сам».** Пиши `src/lib/math/parse.ts`, `docs/DESIGN.md` раздел 7. Никогда не пиши «изучи весь репозиторий».
5. **Доки читай по разделам.** Файлы в `docs/` большие (десятки и сотни КБ). Тебе достаточно написать: «Покажи оглавление `docs/DESIGN.md` и прочитай только раздел 7». Codex сам найдёт заголовки (`rg -n "^#" docs/DESIGN.md`; нет `rg` — любым поиском строк, начинающихся с `#`) и прочитает только нужные строки.
6. **Не читай** `node_modules/` (кроме гайда Next.js), `package-lock.json`, `.next/`, `public/media/` и `reference/` целиком. Из `reference/` — один нужный файл.
7. **AGENTS.md — компактный, не больше 20 KiB = 20 480 байт** (правило `AGENTS.md`, раздел 2). Проверка — попроси Codex: «Сколько байт в AGENTS.md?» (`wc -c AGENTS.md`; в PowerShell — `(Get-Item AGENTS.md).Length`).
   - Лимит Codex — 32 KiB на все AGENTS.md вместе (включая личный `~/.codex/AGENTS.md`), остальное обрезается. Поэтому у проектного — запас.
   - Русская буква занимает 2 байта, поэтому 32 KiB — это около 16 000 русских символов.
   - Каждый байт AGENTS.md грузится в **каждый** чат. Тяжёлое держим в `docs/` и даём ссылкой.
   - Новое правило добавляй, только когда ошибка **повторилась**.
   - Без противоречий: GPT-6 Astra на противоречиях останавливается и переспрашивает.
8. **Сначала план.** На большой задаче `/plan` дешевле, чем переделка.
9. **Модель — по задаче.** Механика на Luna примерно в 20 раз дешевле, чем на Sol. Fast, Max и Ultra не включать.
10. **Тесты дешевле глаз.** Тест ловит ошибку за секунды и потом ловит её всегда. Для справки: в Informatica к этапу 2 было 467 юнит-тестов и 6 e2e.
    - В работе запускай один файл тестов: `npx vitest run tests/<файл>.test.ts`. Полный прогон — в конце.
    - Из логов бери только ошибки.
11. **Повторяй готовое, а не генерируй заново.** Генераторы и проверку ответов делает **код** — это бесплатно и без ошибок.
    - Игры — движки на общем банке заданий: новая тема = новый генератор, а не новая игра.
    - Урок — по шаблону, компоненты — из `src/components/ui`.
    - Перед новым кодом проси: «Найди похожее в `src/` и `reference/` и используй его».
12. **Короткие ответы.** «Отчёт 5–10 строк, без пересказа кода».
13. **Повторяющийся промпт превращай в skill** (раздел 14). В контекст сначала попадает только имя и описание skill, полный текст — когда skill нужен.
14. **Иллюстрации — SVG-кодом** (маскот, сцены), а не генерацией картинок: она тратит лимит в 3–5 раз быстрее.
15. **В облако — только то, что действительно долго или параллельно.** Облачные задачи могут стоить дороже локальных.
16. **Стабильные инструкции** (совет). Кэшированный вход в API в 10–20 раз дешевле обычного, поэтому одинаковое начало чата (AGENTS.md) выгоднее, чем постоянно меняющиеся правила. Как именно кэш работает в Codex, не описано — **проверить**.
17. **Внутри приложения — та же экономия:** код → дешёвая модель → средняя. `docs/AI.md`, раздел 10.

## 7. Независимое ревью

**Зачем.** В Informatica независимый ревьюер **каждый раз находил настоящие баги**, хотя исполнитель уже прогнал тесты. Поэтому ревью после каждого исполнителя обязательно. Примеры того, что он нашёл:
- холст решения стирался при проверке ИИ;
- в «Работе над ошибками» одна ошибка записывалась дважды, а ссылка на урок терялась;
- запрос с телом `null` давал ошибку 500 вместо 400;
- последний ввод в заметках терялся при быстром уходе со страницы;
- лимит ИИ показывался как «ошибка связи»;
- русские «ИИ» и «ошибок: N» были вшиты прямо в казахский интерфейс;
- генератор иногда давал 2–3 варианта ответа вместо 4;
- двойной клик «проскакивал» экран итогов, а двойной тап пропускал разбор ошибки;
- цифры, набранные в калькуляторе, выбирали вариант ответа в уроке;
- большие числа округлялись неточно.

**Как.**
1. **Новый чат, Sol · Medium.** Ревьюер не должен видеть рассуждения исполнителя (совет): так он смотрит свежим взглядом.
2. **`/review`.** Можно проверить:
   - незакоммиченные изменения;
   - ветку против основной;
   - отдельный коммит;
   - со своей инструкцией, например `/review Focus on edge cases and security`.

   Локальный `/review` тратит общий лимит.
3. **Фокус для ревьюера** — раздел «Code Review Rules» в `AGENTS.md` и список рисков ниже. Проси: «Для каждой проблемы — файл и строка, что сломается, как повторить. Сначала самое опасное».
4. **Исправить и повторить `/review`.** Повторять, пока не останется серьёзных проблем.
5. **В GitHub:** комментарий `@codex review` в PR или автоматическое ревью всех PR. Codex в GitHub отмечает только серьёзные проблемы (P0/P1) и следует разделу `## Code Review Rules` в `AGENTS.md`. Это ревью считается отдельно («Code Review usage»). Есть ещё `@codex fix …`. Для справки: в самой OpenAI Codex ревьюит 100 % PR.

**Список рисков** (из багов Informatica; для математики добавлено своё):
- [ ] двойной тап или клик: два ответа, «Готово» проскакивает разбор;
- [ ] Enter: автоповтор, двойное срабатывание, Enter из калькулятора уходит в урок или игру;
- [ ] гонки и таймеры: не очищены при уходе со страницы, нет паузы в скрытой вкладке;
- [ ] `onFinish` игры вызывается дважды; `setState` синхронно в эффекте; прогресс меняется мимо стора;
- [ ] маршрут ИИ: нет лимита, обрезки входа или лога; тело `null`; размер картинки проверяется после регулярного выражения; подсказка выдаёт ответ;
- [ ] ключ или секрет попадает на клиент (`NEXT_PUBLIC_`);
- [ ] ответ посчитан не кодом или неверно; нет теста;
- [ ] **математика:** дробные числа (`0,1 + 0,2`), запятая и точка, `−` и `-`, `0,5` = `1/2`, деление на 0, корень из отрицательного, огромные числа;
- [ ] нет kk, строка вшита в компонент, глагол с родом, эмодзи, цвет мимо токенов, KaTeX с жёстким цветом в тёмной теме;
- [ ] формула вылезает за 360 px; «Меньше анимаций» не выключает анимации.

## 9. Git: коммиты, ветки, PR

### 9.1 Понятия простыми словами

| Слово | Что это |
|---|---|
| **коммит** | сохранение. К нему всегда можно вернуться |
| **ветка** | отдельная линия работы. `main` — это сайт для учеников (продакшен) |
| **push** | отправить коммиты на GitHub. Vercel сразу собирает сайт |
| **PR (pull request)** | запрос «влить ветку в `main`»: видно, что изменилось, сюда пишут ревью |
| **merge** | слить ветку в `main`, то есть выложить |
| **diff** | список изменений: что убрали (красным) и что добавили (зелёным) |
| **worktree** | вторая рабочая папка того же репозитория для параллельной работы |

### 9.2 Правила

- **Перед задачей и после неё — точка отката.** Официальный совет OpenAI: «Create Git checkpoints before and after a task». Спроси Codex: «Чисто ли в git?». Если не чисто — сначала закоммитить или разобраться.
- **Одна ветка — на задачу или этап.** Наше соглашение (у Codex своих требований к именам нет; решение #29):
  - этапы — `etap-<номер>` (например `etap-1-5a`);
  - уроки — `lesson-<id>`;
  - навыки — `bank-<навык>`;
  - сцены — `scene-<вид>`;
  - игры — `game-<id>`;
  - баги — `fix-<коротко>`;
  - документы — `docs-<дата>`;
  - вычитка — `kk-<дата>`;
  - промпты ИИ — `ai-prompt-<коротко>`.

  Полный список с редкими ветками — `docs/PROMPTS.md`, раздел 2, «Ветки».
- **Коммиты — по-русски, коротко:** «Урок fr-1: дроби на числовой прямой».
- **Нельзя без «ок» владельца:**
  - `git push --force`;
  - push или merge в `main` (это выкладка);
  - удаление id уроков и навыков, на которых есть прогресс учеников;
  - смена ключа хранилища `matematika-v1`.
- **PR создаёт Codex.** Владелец сливает после проверки превью. После слияния ветку можно удалить кнопкой в GitHub.
- **Ветки-эксперименты** в `main` **не сливать**. Из такой ветки отдельной задачей переносится только выбранное. Пример: в Informatica по решению #19 запланирована ветка `video-lab` — один ролик в 4 стилях по промпту для Codex; на 2026-10-03 результат не получен, стиль не выбран. В Matematika то же — П-3.4 (по желанию), `docs/DECISIONS.md`, #19.
- **Облачная задача** заканчивается diff'ом. Дальше — «commit or open a pull request».

### 9.3 Что сказать Codex

- «Создай ветку `lesson-fr-1` от `main` и работай в ней».
- «Покажи, какие файлы изменены и что в них поменялось, простыми словами».
- «Закоммить с сообщением „…“ и запушь ветку. Дай ссылку на превью Vercel».
- «Создай PR в `main` с описанием: что сделано, как проверить».
- «Верни все файлы к последнему коммиту». Только если всё хорошее уже закоммичено: несохранённое пропадёт.

## 10. Vercel: превью и продакшен

| | Превью (Preview) | Продакшен (Production) |
|---|---|---|
| Когда собирается | push в любую ветку, кроме `main` | слияние в `main` |
| Адрес | служебный, вида `matematika-<хэш>-….vercel.app`; Vercel также пишет ссылку в PR | основной домен проекта `<проект>.vercel.app`. Если имя занято, Vercel добавит суффикс: у Informatica адрес `informatica-chi.vercel.app` |
| Кто может открыть | только тот, кто вошёл в Vercel (служебные адреса закрыты входом) | все |
| Для чего | владелец проверяет этап на телефоне | ученики и тестеры |

- **Тестерам давай только адрес продакшена.** Урок Informatica: после первой публикации тестерам отправили служебную ссылку, и «сайт не открывался с других устройств». Это было замечание № 1 из 25. Перед отправкой открой ссылку **с чужого телефона**.
- **Сборка упала:** Vercel → Deployments → упавшая сборка → Build Logs. Скопируй Codex **только текст ошибки**, а не весь лог.
- **Продакшен сломался:** сначала верни прошлую рабочую выкладку (Vercel → Deployments → прошлая сборка → откат; кнопка называется Instant Rollback или Promote — **проверить**). Чинить потом, спокойно, в ветке.
- **Расход ИИ:** Vercel → Logs → фильтр `[ai]`. Видны строки `route=… model=… in=… out=…`.
- **Переменные:** Settings → Environment Variables. Поменял — сделай Redeploy.

## 11. Если Codex застрял или что-то сломал

## 12. Безопасность

- **`OPENAI_API_KEY` хранится только в двух местах:** `.env.local` на компьютере и Environment Variables в Vercel.
  - Не в коде и не с префиксом `NEXT_PUBLIC_`.
  - Не в доках, не в чате с Codex, не на скриншоте.
  - Серверные файлы начинаются с `import "server-only";`.
- **Урок Informatica:** тестовый ключ однажды передали в чате, и для продакшена пришлось выпускать новый.
  - **Ключ утёк** (попал в git, в чат, в скриншот) — сразу отзови его на platform.openai.com, выпусти новый и замени в Vercel и в `.env.local`.
- **В облако Codex ключ не класть** (1.5). Если очень нужно — Network secret для `api.openai.com` и отдельный ключ с жёстким лимитом. В старом облачном режиме («Legacy») секреты доступны только скрипту установки и удаляются до начала работы агента.
- **Локальный Codex видит все файлы проекта, включая `.env.local`** (совет). Не проси показать его содержимое. Если ключ всё же появился в ответе Codex, считай, что он утёк.
- **Отдельный проект OpenAI** с жёстким месячным лимитом и оповещением на 50 % (1.7). При превышении лимита API отвечает `429`, а приложение продолжает работать без ИИ.
- **Права Codex — «Ask for approval».** Прежде чем разрешить команду, прочитай, что она делает. Непонятно — спроси.
- **Вход в Codex — через ChatGPT,** не по API-ключу (1.1).
- **Перед первым коммитом:** `git check-ignore .env.local` (1.4).
- **Данные от пользователя — недоверенные.** Ответ ИИ показывается только через `Markdown`, без сырого HTML. Подробно — `docs/AI.md`, раздел 9.

## 13. Документация после каждой задачи

Документация — память проекта между чатами. Без неё следующий чат начинает с нуля и тратит лимит на то, чтобы заново разобраться в проекте.

| Файл | Когда | Что и как |
|---|---|---|
| `docs/CHANGELOG.md` | **каждая задача** | Сверху: `## ГГГГ-ММ-ДД · vX.Y.Z — тема`. Подзаголовки — только нужные, в этом порядке: «Как делали» (какие модели что делали, что нашёл ревьюер), «Сделано», «Контент», «Промпты ИИ (`src/server/prompts.ts`)», «Модели ИИ» (смена `OPENAI_MODEL_*` или `reasoning_effort`), «Казахский», «Ещё нет / Проверить человеком / Известные ограничения». **Изменение промпта ИИ — отдельной строкой.** Порядок, правила и образец записи — в комментарии в начале `docs/CHANGELOG.md` (его не удалять) |
| `docs/ROADMAP.md` | **каждая задача** | Отметить ✅, добавить новые планы 💡 |
| `docs/HANDOFF.md` | **конец сессии и перед новым чатом** | Дата; что сделано; где остановились; следующая задача и модель для неё; вопросы владельцу; адреса (сайт, ветка) |
| `docs/DECISIONS.md` | принято решение | `### #N · ГГГГ-ММ-ДД · Название`, затем **Решение / Почему / Альтернативы / Пересмотреть**. Решение меняет правило — поправить и `AGENTS.md` |
| `docs/ARCHITECTURE.md` | поменялось «как работает» | Только изменившийся раздел |
| `AGENTS.md` | ошибка повторилась или появилось правило | Одна короткая строка; размер не больше 20 480 байт (раздел 6, правило 7) |
| `docs/tasks/<имя>.md` | перед тем как отдать работу исполнителю | ТЗ по шаблону 4.3; папку создаёт первое ТЗ |
| `docs/PROMPTS.md` | нашёлся удачный повторяемый запрос | Добавить шаблон |

**Версии** (как в `docs/CHANGELOG.md` и `docs/ROADMAP.md`, раздел 1):
- пока идёт этап 1 — по одной версии на промпт: П-1.1 → `v0.0.1` … П-1.9а → `v0.0.12` (номер — в строке «Документы» каждого промпта);
- П-1.9б и приёмка этапа 1 → `v0.1.0`; дальше принят этап N — `v0.N.0`;
- исправления — следующий свободный номер по правилу `docs/ROADMAP.md`, раздел 1;
- этап 11 — `v1.0.0`.

В Matematika вторая цифра версии — номер принятого этапа. У Informatica нумерация сдвинута: v0.1–v0.2 были до этапа 1 (первый урок, мини-игры, первая публикация), поэтому там этап 1 — v0.3.0, этап 2 — v0.4.0.

**Пиши честно.** Разделы «Ещё нет», «Нужно проверить человеком» и «Известные ограничения» обязательны. Пример из Informatica: «звук и вибрация не проверены на реальном телефоне», «казахский вычитан только моделью».

Образец записи (например, `## 2026-10-20 · v0.0.5 — этап 1.5а: проверка ответов по значению`) — в комментарии в начале `docs/CHANGELOG.md`.

## 14. Skills: повторяющиеся запросы

Если один и тот же запрос пишется в третий раз, его пора превратить в skill: это и дешевле, и надёжнее.

- **Где лежат:** `.agents/skills/<имя>/SKILL.md` в репозитории; работают и в облачных задачах. В начале файла (front-matter) обязательны поля `name` и `description`. Рядом можно положить `scripts/` и `references/`.
- **Как вызвать:** явно — `$имя` или `/skills`. Неявно — Codex сам выберет skill по `description`.
- **Как создать:** «`$skill-creator` сделай skill …» или вручную. Один skill — одна работа.
- **Какие нужны Matematika** (совет; создать, когда процесс устоится):
  - `new-lesson` — урок по ТЗ и `docs/LESSON_METHOD.md`;
  - `review-kk` — вычитка и применение правок;
  - `precommit` — проверки, документация, отчёт;
  - `handoff` — обновить HANDOFF и предложить следующий шаг.

```markdown
---
name: precommit
description: Финальная проверка задачи перед коммитом в Matematika — команды, документация, отчёт владельцу.
---
1. Запусти `npm run typecheck && npm run lint && npm test && npm run build`. Из вывода покажи только итог и ошибки.
2. Если менялся UI — напомни владельцу проверить 390 px, тёмную тему, kk (docs/DESIGN.md, раздел 14).
3. Обнови docs/CHANGELOG.md, docs/ROADMAP.md, docs/HANDOFF.md (docs/WORKFLOW.md, раздел 13).
4. Отчёт 5–10 строк: что сделано, как посмотреть, что проверить человеку, следующий шаг и модель.
```

## 15. Ритм работы

**Начало сессии**
- [ ] В git чисто («Чисто ли в git?»).
- [ ] Новый чат; модель выбрана по разделу 5.3.
- [ ] Первое сообщение: «Прочитай `docs/HANDOFF.md` и текущий этап в `docs/ROADMAP.md`. Где мы и что дальше — 3–5 строк. Код не меняй».
- [ ] Задача написана по шаблону 4.2 или взята из `docs/PROMPTS.md`.

**Конец задачи**
- [ ] Проверки зелёные, вывод показан.
- [ ] `/review` в новом чате, найденное исправлено.
- [ ] CHANGELOG, ROADMAP, HANDOFF обновлены (DECISIONS и ARCHITECTURE — если нужно).
- [ ] Коммит и push ветки; ссылка на превью получена.
- [ ] Отчёт: что посмотреть на телефоне.

**Конец дня**
- [ ] Всё закоммичено и запушено; HANDOFF актуален.

**Регулярно**
- [ ] Раз в 1–2 недели — остаток лимита Codex (https://chatgpt.com/codex/settings/usage).
- [ ] Раз в месяц — расходы OpenAI API (platform.openai.com) и логи `[ai]` в Vercel.
- [ ] Раз в 2–4 недели — свежие CHANGELOG, DECISIONS и HANDOFF образца Informatica у его владельца → Т-14 «Сверка с образцом» (`docs/PROMPTS.md`). `reference/` не править: новый снимок кладётся целиком, с датой в `reference/README.md`.

**Как говорить с Codex, если ты не программист**
- Описывай, **что видишь**, а не как чинить. Например: «на телефоне кнопка „Проверить“ уезжает под клавиатуру». Прикладывай скриншот.
- Не понял ответ — «объясни проще, что мне нажать».
- Решение «на вкус» — «покажи 2–3 варианта».
- Codex предлагает что-то необратимое или платное — сначала спроси «зачем и что будет».

## 16. Словарик

| Слово | Значение |
|---|---|
| **контекст** | всё, что модель «держит в голове» в этом чате: правила, файлы, переписка. Чем больше контекст, тем дороже каждый шаг и тем хуже качество |
| **токен** | кусочек текста, из них считают расход. Русский текст обычно занимает больше токенов, чем английский |
| **reasoning / усилие** | сколько модель думает перед ответом: дольше — точнее и дороже |
| **субагент** | помощник, которого Codex запускает внутри задачи; тратит свои токены |
| **skill** | сохранённая инструкция для повторяющейся работы |
| **ТЗ** | техническое задание: точное описание, что сделать и как проверить |
| **прораб / исполнитель** | сильная модель планирует и проверяет, дешёвая делает по ТЗ |
| **тест / e2e** | программа, которая проверяет программу; e2e проходит сайт как живой ученик |
| **typecheck / lint / build** | проверка типов, правил кода и сборки |
| **превью / продакшен** | закрытая проверочная версия сайта и сайт для всех |
| **CI** | автоматическая проверка на GitHub при каждом PR и push в `main`: typecheck, lint, test. Зелёная галочка — всё в порядке. Без build и e2e: сборку проверяет Vercel |
| **env-переменная** | настройка вне кода, например ключ или имя модели; хранится в `.env.local` и в Vercel |
